  Because the hidden main element's scrollTop is already 0, revealListTop returns wasAtTop: true, causing !triggerRevealListTop() in manhwaStrip.js line 2377 to evaluate false, prematurely failing to hold boundary navigation.

Finding 10: Modal prompt focus hijacking and restoration failures across detached windows
- Priority: P2
- Confidence: 95%
- Location: src/js/main/passwordOverlay.js:36, 103, 108-115; src/js/main/urlOverlay.js:51-53, 150; src/js/shared/workspaceControls.js:58; src/js/services/actions.js:264
- Attribution: Introduced in a628e57 and omitted from the focus coordination introduced in 35f38e9.
- Affected windows: main, workspace-file-list
- Ownership: Modal dialog lifecycle and OS focus coordination (passwordOverlay.js, urlOverlay.js, workspaceControls.js).
- User sequence:
  Sequence A (Password overlay):
  1. Detach File List into a secondary window.
  2. In the detached File List, select a password-protected archive.
  3. The password prompt appears in the main viewer window.
  4. Type the password immediately on the keyboard without manually clicking into the main window.
  Sequence B (URL / Password prompt cancel):
  1. Trigger Open URL (Ctrl+I) from the detached File List window. Main acquires focus and displays the URL prompt.
  2. Press Escape to cancel the prompt.
- Expected result:
  In Sequence A, the main window acquires native OS focus so keystrokes type directly into the password field.
  In Sequence B, cancelling returns native OS keyboard focus to the initiating File List window.
- Actual result:
  In Sequence A, the prompt opens in main but main never invokes window.setFocus(). OS focus remains with workspace-file-list. Keystrokes trigger file list search rather than password entry.
  In Sequence B, cancelling executes _focusFileList() on main, calling fileListUl.focus() on a hidden DOM element (display: none). Focus is lost in a vacuum and is not restored to workspace-file-list.
- Causal chain:
  In passwordOverlay.js, _show is triggered by Core.onStateChange, not an action dispatch. It runs requestAnimationFrame(() => _input.focus()). Without calling window.getCurrentWindow().setFocus(), DOM focus cannot steal focus from another native OS window.
  When cancelled via Escape, both passwordOverlay.js line 103 and urlOverlay.js line 52 invoke _focusFileList(). On main, fileListUl has display: none in detached mode, so the focus call fails silently. Neither overlay transmits an RPC request to focus workspace-file-list.

Risk 01: Inter-window request flood during gallery scroll in detached File List
- Priority: P2
- Confidence: Medium
- Trigger / Location: src/js/filepanel/filePanel.js:2115; src/js/urlLoader.js:2661; src/js/shared/workspaceSession.js:61
- Condition: Scrolling the detached File List during an active gallery download executes renderVisibleRows, which synchronously calls setDownloadVisibleRange. urlLoader.js forwards this via requestWorkspace('main', 'url', 'setVisibleRange', [start, end]). Each call creates a pending request entry with a 30s timeout. Rapid scrolling generates dozens of requests per second. If pending.size reaches MAX_PENDING_REQUESTS (128), workspaceSession.js rejects with "Too many pending workspace requests", logging errors and dropping range synchronization.
- Runtime observation needed: In detached mode, open an active downloading gallery with over 200 items. Rapidly scroll the detached File List using a free-spinning mouse wheel or continuous scrollbar drag. Monitor the DevTools console in both windows for "Too many pending workspace requests" rejections.

Risk 02: Replica download status path separator mismatch on Windows
- Priority: P3
- Confidence: High
- Trigger / Location: src/js/urlLoader.js:2640, 2797-2798
- Condition: In urlLoader.js line 2640, getGalleryDownloadStatus on the replica performs direct map lookup: _workspaceStatuses.get(filePath). Unlike main, it does not normalize backslashes to forward slashes. On Windows, if download status events transmit normalized paths (/), while filePanel queries with Windows native paths (\), the map lookup returns undefined. isPlaceholderFile returns false, potentially treating pending download files as missing.
- Runtime observation needed: On a Windows machine, start a gallery download in detached mode. Check whether downloading rows in the detached File List display download spinner badges or render broken file icons.

Risk 03: Library relocation event ignored by replica thumbnail caches
- Priority: P3
- Confidence: Medium
- Trigger / Location: src/js/main/main.js:341-346; src/js/filepanel/filePanel.js:85-88
- Condition: When Library relocation occurs, the backend emits library-relocated. In main.js line 342, the listener aborts early with 'if (workspaceSurface) return;'. The main window calls clearLibraryPathCaches(), but its local cache is unpopulated in detached mode. In workspace-file-list, clearLibraryPathCaches() is never called, leaving thumbnailCache and favoritesThumbnailCache populated with stale path keys until LRU eviction occurs.
- Runtime observation needed: In detached mode, browse Library items so thumbnails are cached in the detached window. Open Options, relocate the Library folder to a new location, save, and browse Library items again. Check if old thumbnails persist or cause cache collisions.

Risk 04: Initial attachment visible strip range race condition
- Priority: P3
- Confidence: Medium
- Trigger / Location: src/js/shared/workspaceControls.js:7, 20-24; src/js/shared/workspaceSession.js:114-117
- Condition: When workspace-file-list sends { kind: 'ready' }, main responds with a state snapshot. quivit-workspace-strip-info is not part of the state snapshot; it is an independent event fired only on state changes and scroll settle. Upon initial attachment, remoteVisibleIndices in workspace-file-list is initialized to []. Until the first scroll or selection change on main, .is-visible-in-strip is not applied to multi-image visible ranges.
- Runtime observation needed: Open a container in Manhwa view, then detach the File List into a secondary window. Observe whether visible strip images immediately have .is-visible-in-strip applied in the detached File List before any interaction.

Risk 05: Windows OS foreground lock on programmatic window focus
- Priority: P3
- Confidence: Medium
- Trigger / Location: src/js/shared/workspaceControls.js:58; src/js/services/actions.js:258-264; src-tauri/src/windows.rs:113
- Condition: When cmd-use-url (Ctrl+I) is triggered from workspace-file-list, workspaceControls.js line 58 calls window.setFocus() on main. Under Windows LockSetForegroundWindow policy, programmatic focus transfers between windows without direct user interaction on the target window can cause the target taskbar icon to flash rather than taking foreground focus immediately. Furthermore, cmd-open-dir and cmd-open-file do not declare focusOwner: true in actions.js, opening native dialogs parented to main while main may be unfocused or behind the secondary window.
- Runtime observation needed: In detached mode, activate the File List window and press Ctrl+I and Ctrl+O. Observe whether the main window and native dialog immediately take active foreground keyboard focus or if the taskbar icon flashes.

Risk 06: Native window titlebar close on Options dropping async preview reversion
- Priority: P2
- Confidence: Medium
- Trigger / Location: src/js/options/options.js:363-366; src-tauri/src/windows.rs:202-223
- Condition: In Options, clicking the Close button explicitly awaits revertPreviewChanges() before closing. However, clicking the native titlebar X fires onCloseRequested without prevent_close() installed. The handler begins an async task awaiting revertPreviewChanges() while the webview process terminates. If the process exits before 'theme-preview' or 'css-preview' are serialized and emitted, preview changes in workspace windows will not revert.
- Runtime observation needed: Open Options, preview a contrasting theme, and immediately click the native window close button (X). Observe whether the workspace windows revert to the saved theme.

Risk 07: Second application instance launch not unminimizing detached File List window
- Priority: P3
- Confidence: Medium
- Trigger / Location: src-tauri/src/lib.rs:46; src-tauri/src/windows.rs:378-388
- Condition: In lib.rs line 46, the single instance handler calls main_window.unminimize(), followed by windows::restore_from_tray(app). restore_from_tray calls window.show() on secondary windows. On Windows Win32, calling ShowWindow with SW_SHOW on a minimized window does not unminimize it (SW_RESTORE is required).
- Runtime observation needed: In detached mode, minimize both main and workspace-file-list to the Windows taskbar. From Windows Explorer, double-click an associated image file. Observe whether workspace-file-list unminimizes alongside main.
